### 2.2 默认值与三态语义

`languageMode` 默认 **空串**（`MODE_UNSET`），不是 `'auto'`。这不是风格选择，而是迁移规则的前提：空串表示「用户从没表态过」，由 `effectiveMode()` 结合 `targetLanguage` 判定；显式 `'auto'` / `'manual'` 才表示用户表过态。

## 三、Host 解析层

### 3.1 解析器是纯函数

`lib/language.js` 151 行，**无任何 `import` / `require`**，不引用 `ctx` / `fs` / `process` / `globalThis`，模块头注释（`lib/language.js:4-6`）明确「纯函数模块：不 import 任何 ctx、不读磁盘、不碰配置对象」。这是能被 `scripts/verify-language.mjs` 直接单测的前提，也是「算错」类缺陷可回归的前提。

### 3.2 界面语言的读取链路（describe 只调一次，manual 态连调都不调）

| 环节 | 位置 | 实测 |
| --- | --- | --- |
| 缓存变量 | `lib/index.js:138` | `let cachedPreference = null` |
| 读取函数 | `lib/index.js:144-156` | `settings.describe()` → `rows.find(item => item?.ns === 'locale')` → `row?.value?.preference`；异常吞掉返回 `null` |
| 刷新函数 | `lib/index.js:163-171` | 首行即 `if (currentMode() === MODE_MANUAL) { cachedPreference = null; return; }` —— **manual 态直接返回，不调 describe** |
| 首次调用 | `lib/index.js:249` | `apply` 期（`ctx.inject(['settings'], …)` 子级内） |
| 事件刷新 | `lib/index.js:258-262` | `child.on('settings/document-updated', (ns) => { if (ns === 'locale' \|\| ns === 'language-guard') refreshPreference(child.settings); })` |
| 文本读取 | `lib/index.js:104`、`lib/index.js:231` | 两处只把 `preference: cachedPreference` 传进 `resolveLanguage` / `resolveSource` |

`readLocalePreference()` 全仓只被 `refreshPreference()` 调用一次（`lib/index.js:168`），因此 **`text()` 路径上没有任何磁盘 I/O 或投影遍历**——这一点很关键：三段 system prompt 每次装配都会执行 `text()`，若在那里调 `describe()`（单次约 0.79 ms 读盘 + 1.17 ms 投影），会把成本乘进每个 step。

### 3.3 上游契约核实（为什么 `ns === 'locale'` 是对的）

| 事实 | 证据 |
| --- | --- |
| `describe()` 的行确实带 `ns` 与 `value` | `/dsh/node_modules/@deepseek-ai/dsh-settings/lib/index.js:432`、`:443` `ns: entry.options.id`，`:444` `value: projectForm(...)` |

## 四、Client 层

### 4.1 同源缺陷已修（本轮最需要独立核实的一项）

初版 Client 读 `ctx.locale.getSnapshot().active`，与 Host 的 `describe().locale.preference` 在「用户从未在 DSH 设置里选过界面语言」时必然分叉。修复后的实测：

| 断言 | 命令 | 结果 |
| --- | --- | --- |
| 常量定义 | `grep -n "UI_LOCALE_NS" client.js` | `client.js:419` `const UI_LOCALE_NS = 'locale'` |
| 读取函数 | `grep -n "function useUiPreference" client.js` | `client.js:443`，`:446-453` 读 `configForms.get(UI_LOCALE_NS).getSnapshot().value.preference`，`:457-485` 订阅并在卸载时 off |
| 调用点 1 | `client.js:719` | `useUiPreference(props.configForms)` |
| 调用点 2 | `client.js:1058` | `useUiPreference(props.configForms)` |
| slot 是否真给 `configForms` | `client.js:1296`、`client.js:1333` | 两处 `inject: () => ({ …, configForms: ctx.configForms, … })` |
| 旧路径是否清除 | `grep -c "locale.getSnapshot" client.js` | **1**，且是注释（`client.js:424` 解释「为什么不读 active」） |
| 旧变量是否清除 | `grep -c "localeFace" client.js` | **0** |

**「同源」不是靠两处都写了 `describe` 来保证的，而是靠上游同一个 mirror。** 独立核实：

- `/dsh/node_modules/@deepseek-ai/dsh-client-ui-settings/lib/client.js:1080` `ConfigFormController`，`:1116-1118` `this.unsubscribe = mirror.subscribe(() => this.derive())`；
- 同文件 `:1287` `describe() { return this.mirror; }`、`:1297` `new ConfigFormController(this.owner, { namespace: entryId }, this.mirror, this.schema)`；
- 同文件 `:1240-1300` `ConfigForms` 服务：`get(entryId)` 返回的表单与 `describe()` **共用同一个 `this.mirror`**。

即 Client 的 `configForms.get('locale').getSnapshot().value` 与 Host 的 `describe()` 是**同一次 describe 的两个投影**，不存在「各读各的、恰好一样」的可能。且官方 `dsh-client-locale` 自己就是这么读的（见 3.3 表），说明这不是我们的私货路径。

## 五、映射规则

### 5.1 四条规则逐条实测

| 输入 | 期望 | 实测 |
| --- | --- | --- |
| `'zh'` | `'zh-CN'` | `'zh-CN'` |
| `'en'` | `'en'` | `'en'` |
| `'ja'`（其他合法 id） | 原样 | `'ja'` |
| `'zh-TW'` | 规则 3 原样，但被规则 1 的 `primary === 'zh'` 覆盖 | `'zh-CN'` |
| `null` / `''` / `'!!!'` | `null`（调用方兜底） | `null` |

`'zh-TW' → 'zh-CN'` 这个「被覆盖」是**有意的**：DSH 内置界面语言只有 `zh` 与 `en`（`dsh-client-locale/lib/index.js:11` `LOCALE_IDS = ["zh","en"]`），`zh` 不区分简繁，Host 侧也没有系统语言信号可用。要繁体必须切手动并手选 `zh-TW`——README 两版与设置卡片的已知限制都写明了。

### 5.2 归一化与合法性

- `normalizeLocaleId`（`lib/language.js:52-58`）：`trim` → 下划线转连字符 → BCP-47 正则（`lib/language.js:39` `^[A-Za-z]{2,3}(-[A-Za-z0-9]{2,8})*$`）。
- 14 个边界输入（含 `'zh_Hans_CN'`、`' x '`、`'e'`、`'abcd'`）结果全部合法或正确返回 `null`。
- **70 组** `(mode × preference × fallback)` 组合的解析结果**全部通过 BCP-47 正则**——即无论用户怎么配，注入到 system prompt 里的永远是一个合法标签，不会出现 `undefined` 之类。

### 5.3 `effectiveMode` 四种组合

| `languageMode` | `targetLanguage` | 有效模式 | 实测 |
| --- | --- | --- | --- |
| `'auto'` | 任意 | auto | auto |
| `'manual'` | 任意 | manual | manual |
| `''` | 等于默认 `zh-CN` | auto | auto |
| `''` | 不等于默认（如 `ja`） | manual（老用户迁移保护） | manual |

第四行是迁移规则：0.1.x 的 `cordis.patch.yml` 里可能写着 `targetLanguage: ja` 而没有 `languageMode`，升级后必须继续用 `ja`，不能被自动模式静默覆盖。

### 5.4 与调研文档的偏差（有意）

`04-auto-language.md` §7.3 列了 12 行映射（含 `osLanguages` 简繁细分与 `normalizeOsTag`），但 §0.1 裁决三已把那些判为「未实现的规格」，0.2.0 只实现 4 条。本次实测与裁决一致：代码里没有 `osLanguages` / `normalizeOsTag` 的任何痕迹。

**本节判定：pass。**

### 7.4 教训

**采纳并加强 captain 提出的那条**：「两侧一致性不能只查逻辑一致，还要查输入一致。镜像纯函数防的是『算错』，防不了『喂错』——凡两侧都要显示同一个值的场景，必须先确认两侧的数据源是同一次读取。」

本轮为它补了三条实证：

1. **「同源」必须用上游源码证明，不能靠「两处都写了 describe」自证。** 证据链是 `ConfigForms.get(entryId)` → `new ConfigFormController(owner, spec, this.mirror, schema)` → `mirror.subscribe(() => this.derive())`（`dsh-client-ui-settings/lib/client.js:1240-1300`、`:1116-1118`），而 `describe()` 返回的也是 `this.mirror`（`:1287`）。同一个 mirror 才叫同源。
2. **回归防护要写成「禁止旧写法」的反向断言，而不只是「要求新写法」的正向断言。** M12 同时断言 `! locale.getSnapshot` 与 `! localeFace`，否则删掉新代码、旧代码也早没了的情况下，正向断言仍会通过（因为新写法还在），反向断言才能钉死「不许回头」。
3. **`getSnapshot()` 的形状本身是契约。** 官方 `dsh-client-locale` 的快照是 `{active, locales, revision}`，**不带 `preference`**（`:1216-1220`），所以「用 active 反推 preference」这条路从形状上就不成立；`active` 还会在 `preference === undefined` 时退化成浏览器派生的 `provisional`（`:1344-1345`）。这类「看起来能拿到、实际语义不同」的字段，最容易在两侧对齐时埋雷。

**本轮新增两条纪律教训（评审侧）**：

1. **并发修改期间，任何输出都必须重跑，不能拿几分钟前的 `/tmp` 文件下结论。** 本轮首次实跑得到 `72 PASS / 1 FAIL / exit 1`（R23 报「文档尺寸与实测不符」并列出 4 个历史尺寸），几分钟后同一命令得到 `73 PASS / 0 FAIL / exit 0`；`stat` 显示脚本 mtime `16:33:30` 晚于首次运行 `16:32:35`。若按第一次的结果出报告，会得出完全相反的结论（误判 R23 为「反向断言假阳性」）。**结论：评审报告必须记录基准 commit，并在写结论前重跑一次关键命令。**

2. **看到结果在评审期间变化时，先查 `git status` 与 `git log`，确认是不是有人在并发改，而不是先怀疑环境。**（captain 补充）本轮事后核实：那段时间 captain 正在把 R23 的判据体从「反向断言」改成「正向断言」，并同步文档里过期的 pack 尺寸（53284 → 53657、162435 → 163552），改完提交为 `f1eb0e8`。也就是说，变化不是「未提交版本被改写又还原」这类异常，而是**并发的、有据可查的正常提交**。报告初稿的措辞曾把它写成前者，此处已按事实更正。这条与第 1 条互为前提：第 1 条要求「重跑」，第 2 条要求「重跑后若结果变了，先归因再下结论」——归因错会导致把别人的修复当成环境噪声，从而漏掉真正的基准漂移。
