## 三、执行发布

三步，全部由用户本人执行：

```bash
# 1. 确认工作区干净、与远端同步
git status -sb          # 应为 ## main...origin/main，无改动
git log --oneline -1    # 记录要发布的提交

# 2. 最后一次 dry-run（可选但建议）
npm publish --dry-run

# 3. 真正发布
npm publish --access public
```

关于 `--access public`：`package.json` 里已有 `publishConfig.access: "public"`，因此 `npm publish` 不带参数也会以 public 发布。显式加 `--access public` 只是让意图在命令里可见，两者等价。

**不要**在 dry-run 通过后就认为已经发布——`--dry-run` 不写 registry，必须有一次不带 `--dry-run` 的调用。

发布成功的判断：

```bash
npm view dsh-language-guard version        # → 0.1.0
npm view dsh-language-guard dist.tarball   # → tarball URL
```

发布后立即验证安装：

```bash

ls node_modules/dsh-language-guard         # 应见 client.js、lib/、locale/、cordis.patch.yml
```

## 四、回滚

### 情形 A：刚发布，发现严重问题（72 小时内）

```bash
npm unpublish dsh-language-guard@0.1.0 --force
```

注意事项（以 npm 官方文档为准：<https://docs.npmjs.com/policies/unpublish>）：

- **72 小时窗口**：发布后 72 小时内可自行 unpublish；超过 72 小时需要联系 npm support，且通常只接受安全或法律理由。
- **同版本 24 小时冷却**：unpublish 后，同一版本号在 24 小时内不能再发布。所以「撤销 → 改 → 立刻重发 0.1.0」行不通，等 24 小时或直接升版本号。
- **已被依赖则受限**：如果已有其他包依赖此版本，unpublish 会被拒绝。

### 情形 B：已过 72 小时，或不想撤销

推荐做法是**发一个修复版本**，而不是撤销：

```bash
# 修 bug 后升 patch 版本
npm version patch        # 0.1.0 → 0.1.1，同时打 git tag
git push origin main --tags
npm publish
```

已发布的版本保留在 registry 上，用户可以继续装旧版，也可以升级。

### 情形 C：只回滚 GitHub 仓库

```bash
# 回退到上一个提交（保留历史，不 force push）
git revert <bad-commit-sha>
git push origin main
```

**不要**用 `git reset --hard` + `git push -f` 改写已推送的历史。

## 六、本机未验证的两项（需在有 `dsh` CLI 的环境补做）

R8 的实操部分、R14、R20 都依赖 `dsh` CLI。本机**只有 DeepSeek Harness 桌面应用，没有 `dsh` 命令**：

```bash
which dsh        # → 无输出（PATH 里没有）
```

桌面应用的运行时在 `app.asar` 内（`@deepseek-ai/dsh` 的 `bin` 指向 `lib/bin.js`），但 asar 是归档文件不是目录，`node` 无法直接执行内部路径：

```bash
node "/Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js" --version
# → Error: Cannot find module '.../app.asar/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js'
```

因此以下两项需要在装了 `dsh` CLI 的环境（或桌面应用的插件页）补做：

1. **R20 干净 profile 端到端安装**

   ```bash
   dsh plugin --profile verify-clean add /path/to/dsh-language-guard
   # 或发布后：
   dsh plugin add dsh-language-guard
   ```

   判定：返回体不得出现 `incompatible-version`；随后用 `cordis_inspect_query` 确认本插件行是 `application: applied`。

2. **R14 `engines.dsh` 兼容性**：同上安装过程无版本错误即通过。

3. **R8 的实操部分**：装好后按 `README.zh.md` 的「验证约束确实进了 system prompt」三步走一遍，确认 C/D 档 `三段命中=3/3`、切 B 档 `2/3` 且长度短 118 字符。

替代路径：用桌面应用的**插件页 → 添加插件 → 输入本地绝对路径**安装，同样能完成端到端验证，不需要 CLI。
