## 一、分发方式：npm 为主，GitHub 为备

最终状态是**两条通道都通**。npm 是首选（装法最短），GitHub 是备选（npm 不可达时、或用 tag 锁版本时）。

但这条结论是走弯路换来的，弯路值得记下来：**项目最初放弃过 npm 发布**，因为当时的出口 IP 被 Cloudflare 风控，而命令行注册通道也已被 npm 关闭。当时的实测证据：

| 检查项 | 结果 | 含义 |
| --- | --- | --- |
| `https://www.npmjs.com/signup` | **403**，响应体 `<title>Just a moment...</title>` | Cloudflare 人机验证页 |
| `https://www.npmjs.com/` | 403 | 全站拦截，不只是注册页 |
| `https://www.npmjs.com/login` | 403 | 登录页同样被拦 |
| 直连真实 Cloudflare IP + `--noproxy '*'` | **仍 403** | 排除本地 DNS / 代理干扰 |
| `registry.npmjs.org/-/ping` | **200** | 发布通道本身正常 |
| `npm ping` | `PONG 784ms` | registry 可达 |
| `npm adduser --auth-type=legacy` | `Account creation via legacy auth is unavailable` | 命令行注册已被 npm 关闭 |
| `npm adduser --auth-type=web` | 只给一个仍需浏览器的登录链接 | 注册必须过网页 |

当时的结论：**注册账号必须过浏览器，而浏览器被 Cloudflare 拦住；命令行注册通道已被 npm 关闭。** 于是改用 GitHub 分发，功能上没有任何损失（插件管理器原生支持 Git 地址）。

后来解决的过程，按时间顺序：

1. 换网络注册成功，账号 `sunjingzhi`（邮箱 `dlyh@vip.qq.com`）。
2. 在 npm 后台关联 GitHub 账号 `58fly`，2FA 随之从 `disabled` 变为 `auth-and-writes`——注意这一步**没有**走验证器绑定，所以拿不到 OTP。
3. 发布被 registry 拒绝：先是 `Two-factor authentication or granular access token with bypass 2fa enabled is required to publish packages.`，2FA 开启后变成 `You must provide a one-time pass.`
4. 破解点：`npm publish` 在 TTY 下会走 **web 认证**（输出 `Authenticate your account at: https://www.npmjs.com/auth/cli/<uuid>`，回车开浏览器完成授权），这条路不需要验证器 App，也不需要 OTP。
5. 发布成功：`+ dsh-language-guard@0.2.1`。

> **给未来的自己**：npm 要求发布必须 2FA，但 2FA 的完成方式有两种——验证器 App 的 6 位 OTP，或 CLI 的 web 认证链接。没有验证器不等于发不了包，`npm publish` 直接跑，在 `Press ENTER to open in the browser...` 处回车即可。

## 二·补、本机 profile 的一个既有障碍及修复（与本插件无关，但会挡住安装）

排查 `pnpm add` 失败时发现：本机 desktop profile 的 **`pnpm install` / `pnpm add` 全部失败**，报

```
[ERR_PNPM_INVALID_VERSION_UNION] Invalid versions union.
Found: "@dsh-external/dsh-super-injector@git+https://github.com/yjh051108/dsh-routing-suite.git".
Use exact versions only.
```

**根因**：`pnpm-workspace.yaml` 的 `allowBuilds` 段里有三条 `@dsh-external/dsh-super-injector` 键，其中两条的 key 是 Git spec 而不是精确版本：

```yaml
allowBuilds:
  '@dsh-external/dsh-super-injector': true                                                    # ← 有效
  '@dsh-external/dsh-super-injector@git+https://github.com/yjh051108/dsh-routing-suite.git': true   # ← 无效
  '@dsh-external/dsh-super-injector@https://codeload.github.com/yjh051108/dsh-routing-suite/tar.gz/1952733…': true  # ← 无效
  '@google/genai': true
  protobufjs: true
```

这是 `@dsh-external/dsh-super-injector`（第三方注入器）留下的记录——它自己的 `patches/repair-super-injector.mjs` 注释里就写了「该依赖的版本是 git tarball URL，pnpm 会报 `ERR_PNPM_INVALID_VERSION_UNION` 并让 `pnpm install` 直接失败」。pnpm 11 在解析 `allowBuilds` 的 key 时会做版本联合校验，遇到 git spec 即中止整个安装。

**注意**：`node_modules/.modules.yaml` 里也有一份同样的 `allowBuilds`，但那是 pnpm 的缓存投影，**改它无效**——pnpm 以 `pnpm-workspace.yaml` 为准。第一次修错位置（只改了 `.modules.yaml`）时现象完全不变。

**修复**：只删掉 `pnpm-workspace.yaml` 里那两条带 Git spec 的键，保留按包名的那条（`'@dsh-external/dsh-super-injector': true` 仍然允许它跑构建脚本）。

```bash
cd ~/.dsh/profiles/desktop
cp pnpm-workspace.yaml pnpm-workspace.yaml.bak-$(date +%s)
python3 - <<'EOF'
import io
p = 'pnpm-workspace.yaml'
s = io.open(p, encoding='utf-8').read()
for bad in [
    "  '@dsh-external/dsh-super-injector@git+https://github.com/yjh051108/dsh-routing-suite.git': true\n",
    "  '@dsh-external/dsh-super-injector@https://codeload.github.com/yjh051108/dsh-routing-suite/tar.gz/195273352f23bff7f9023ebe2ec0cdbdf9c98f10': true\n",
]:
    s = s.replace(bad, '')
io.open(p, 'w', encoding='utf-8').write(s)
EOF
pnpm install --lockfile-only     # 退出码 0 即修复
```

**修复后实测**：`pnpm install --lockfile-only` 从「退出码 1 + INVALID_VERSION_UNION」变为「退出码 0，`Done in 4s`」，且 lock 正确写入本插件的 Git 来源：

```yaml
dsh-language-guard:
  specifier: git+https://github.com/58fly/dsh-language-guard.git
  version: https://codeload.github.com/58fly/dsh-language-guard/tar.gz/9ee56fa40811bf1b6d12d8e8df1a7472bccf9c57(@deepseek-ai/schemastery@3.18.5)
```

> 这个修复只影响 pnpm 的构建脚本白名单，不改任何已安装包。若 `@dsh-external/dsh-super-injector` 日后重装并再次写入带 Git spec 的键，需重做一次。

## 十一、0.1.1 变更：约束文本压过 AGENTS.md 一类语言约定

2. **改配置本来就不需要重启**：写入走 `dsh-config-editor`（README：「保存到当前 profile 的 patch 并立即应用」），volatile 字段经 `cordis-plugin-loader` 的 `_commitVolatile` → `loader/volatile-update` 只替换运行中的引用、不重挂插件；system prompt 每次请求重新装配。所以「必须重启」这个猜测不成立。
3. **真正的原因是约束文本压不住中文写成的 AGENTS.md**：0.1.0 的首段只声明「优先于后续任何**英文**内容」。而用户的全局 `~/.dsh/AGENTS.md` 里写着「默认所有对话……都必须使用简体中文」，这是**中文**写成的硬约束，经 `agent-instructions` 以 user 消息注入，落在首段之后。模型据此继续用中文 → 用户看到「选了日语没变化」。

### 0.1.1 的两处修改

## 十三、0.2.0 变更：自动语言模式

### 为什么加

0.1.x 只有一个 `targetLanguage` 字段，装完默认 `zh-CN`。这带来两个实际问题：

1. **界面语言是英文的用户**（或想在英日韩之间切换的用户）每次都要手动改配置，忘了改就一直是中文；
2. 插件本身是**通用语言锁定器**（`01-mechanism.md` 的定位：目标语言可配，默认简体中文），但 0.1.x 的默认值把「默认」和「唯一常用值」混在一起，用户看不出它其实是可跟随的。

0.2.0 引入**语言模式**：`自动`（跟随 DSH 界面语言）与 `手动`（固定使用配置的语言）。默认行为对中文用户完全不变——界面语言是中文时自动解析为 `zh-CN`。

### 一个必须先说清的边界：不读系统语言

「自动」指的是**跟随 DSH 的界面语言**，不是跟随操作系统语言。这不是偷懒，是两条路都走不通：

| 方案 | 实测结论 | 结论 |
| --- | --- | --- |
| 读 Electron 的 `app.getLocale()` | Host 进程以 `ELECTRON_RUN_AS_NODE=1` 运行，`require("electron")` 抛 `Cannot find module 'electron'` | 不可达 |
| 读 Node 的 `Intl.DateTimeFormat().resolvedOptions().locale` | 在该进程里**恒为 `en-US`**，而本机系统实际是 `zh-Hans-CN` | 会把中文用户误判成英文，比不判断更糟 |
| 读 DSH 自己的界面语言偏好（`settings.describe()` 里 `ns === 'locale'` 的 `preference`） | 与官方 `/lib/main.js` 读取界面语言的方式一致，可用 | **采用** |

因此：**任何文档、任何界面文案都不得声称插件会识别系统语言**。这条已写进 `docs/验收清单.md` 的 M 组与 README 的已知限制。

### 配置与升级兼容性

`languageMode` 的 schema 默认值是**空串 `''`**，不是 `'auto'`：

| 改成 `ja` / `en` / `zh-TW` 等 | 手动 | 保留原值，不被界面语言覆盖 |

## 十四、0.2.1 变更：镜像段回归防护 + `defaultLanguage` 兜底修正

0.2.0 发布后，终版复核（`docs/评审报告-0.2.0.md` 第八节）在变异测试里发现一处**回归防护缺口**与一处**两侧不等价**，0.2.1 一并修掉。功能行为对用户**没有任何变化**，这一版纯粹是把「面板显示与实际注入不会分叉」这件事变成机器可守的。

### 14.1 缺口：镜像段零覆盖

`client.js` 里有一段手抄的解析规则（5 个常量 + 5 个函数）。必须手抄是因为 Client 是独立 bundle，`window.__ModuleLoader__.load` 的 factory 只能 `require('react')`，不能相对 import 包内其他文件。**抄两份就必须有判据守住一致性**，而 0.2.0 时这条守护是假的：

| 判据 | 实际覆盖 | 能否抓住 Client 侧漂移 |
| --- | --- | --- |
| `verify-language.mjs` | 只 `import '../lib/language.js'`，**从不读 `client.js`** | 否 |
| M1 | 两侧源文本正则，仅 `mapPreference` 的 zh / en 两条规则 | 部分（文本层） |
| M2 | 两侧源文本正则，仅 `effectiveMode` 的三元式 | 部分（文本层） |
| M3 / M4 | Config 默认值、radio group 结构 | 无关 |
| R23 | 文档 pack 尺寸 | 否（改任何字节都会触发，是副作用） |

实测证据：把 `client.js` 的 `MODE_MANUAL` 改成 `'auto'`，`verify-language.mjs` 仍 exit 0 / FAIL 0；`verify-checklist.sh` 唯一报警的是 R23。若改完代码顺手同步了文档尺寸，**全仓会绿而镜像已经漂移**。

### 14.2 修法：`scripts/verify-mirror.mjs`（清单 M14）

把镜像段从 `client.js` 抽出来（`const BCP47 =` → `/** 语言标签 → 显示名`），拼上 `export { … }` 用 `data:text/javascript;base64,` 动态 import 成真模块，与 `lib/language.js` 逐函数比输出：

- 矩阵 `MODES(10) × LANGS(23) × FALLBACKS(8) × DEFAULTS(6)` + `effectiveMode` 的 `targetLanguage` 维
- **12420 组输入 / 56580 次函数比较**，覆盖 5 个函数与 3 个常量
- 含 `null` / `undefined` / `''` / `'invalid!'` / `'ZH-cn'` / `'  ja  '` / `'zh_CN'` / `0` / `' '`
- 抽取边界缺失或顺序异常 → 明确中文报错 exit 1，不静默通过

`verify-checklist.sh` 的条目数 73 → **74**。

### 14.3 顺带修掉：`defaultLanguage` 兜底两侧不等价

写 M14 时必须把 `DEFAULTS` 维度加入假值，一跑就撞出这处不等价：

| `defaultLanguage` 输入 | Host（默认参数 `= 'zh-CN'`） | Client 原实现 `\|\|` | 若用 `??` |
| --- | --- | --- | --- |
| 省略 / `undefined` | `'zh-CN'` | `'zh-CN'` ✅ | `'zh-CN'` ✅ |
| `null` | **`null`**（原样传入） | `'zh-CN'` ❌ | `'zh-CN'` ❌ |
| `''` | **`''`**（原样传入） | `'zh-CN'` ❌ | `''` ✅ |

JS 默认参数**只对 `undefined` 生效**，`null` 与 `''` 都会原样传入。所以 `||` 与 `??` 都修不好——`??` 只对 `null`/`undefined` 兜底，`null` 那一格仍然分叉。

最终新增 `pickDefaultLanguage()` 精确模拟默认参数语义：

```js
function pickDefaultLanguage(input) {
  const given = input ? input.defaultLanguage : undefined;
  return given === undefined ? DEFAULT_LANGUAGE : given;
}
```

三处（`effectiveMode` / `resolveTargetLanguage` / `resolveSource`）统一改调。

**当前不可达**：Host 唯一调用点恒传真值、Client 两个调用点不传，所以两侧实际恒等，用户行为无变化。但将来若允许自定义默认语言，`||` / `??` 都会让空串或 `null` 在 Client 侧被静默替换成 `zh-CN`——这正是「喂错」的那类分叉，趁现在修掉。

### 14.4 变异验证（M14 不是空转）

| 变异 | `verify-mirror` | 差异数 |
| --- | --- | --- |
| `MODE_MANUAL` → `'auto'` | exit 1 | 常量不等（host `"manual"` / client `"auto"`） |
| `mapPreference` 的 zh 规则 → `'zh-Hans'` | exit 1 | 5942 处 |
| `resolveSource` 去掉 `defaultLanguage` 转发 | exit 1 | 818 处 |
| `pickDefaultLanguage` 改回 `\|\|` | exit 1 | 1374 处 |

## 十六、0.3.0 变更：补齐工具调用描述通道 + 生效可见性（竞品评估驱动）

### 16.1 为什么发这一版

对同类插件 [`dsh-agent-lang`](https://github.com/KannaKuron/dsh-agent-lang) 做了一次逐行对比评估（产品 / UX / 架构三方独立分析后交叉核对）。结论是**对方不是整体更优**：它宣传的「runtime context 渲染在请求末尾、近因压过工具说明」被它自身的去重逻辑削弱——宿主 `RuntimeContextProjection.project` 里有 `if (this.retained?.text === snapshot) return;`，文本不变就不产生新消息，那条指示在首次提交后即沉入历史中段。本插件的三个 section 每步在固定 order 重新渲染，反而是真实优势。

### 16.2 改动

**① 工具调用描述通道（真实功能缺口）**

## 十七、发布纪律：npm 与 GitHub 强制对齐

0.3.0 发布时暴露出一个流程漏洞：npm 上已经有 0.3.0，GitHub 上却没有对应的 commit 与 tag。这类漂移没有任何机制拦截，只能靠人记得。

现在写入铁律并做了机器强制。

### 17.1 铁律

**npm registry 上 `dsh-language-guard` 的每个已发布版本，都必须在 GitHub 仓库里有对应的 commit 与 tag；GitHub `main` 的 `package.json` 版本号必须等于 npm 的 `latest`。**

不接受「下次补」「先发再说」。npm 发布不可逆（unpublish 受 72 小时限制且会破坏已安装用户），GitHub 可改可补，所以顺序只能是 Git 先行。

### 17.2 强制机制

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| 铁律与流程 | `AGENTS.md` | 项目级最高优先级约束，DSH 每个会话自动注入 |
| 发布前置检查 | `scripts/verify-release.mjs`（`prepublishOnly` 自动调用） | 工作区必须干净、`HEAD` 上必须有 `v<version>` tag、tag 之后进包内容未变（见下方 17.2.1），任一不满足 `npm publish` 直接失败 |
| 发布后自检 | `npm run verify:release` | 本地版本 / npm `latest` / git tag 三方比对，并反向检查 npm 上有而 GitHub 无 tag 的版本 |

`prepublishOnly` 只在 `npm publish` 时执行，用户 `npm install` 本包时不会跑，因此不构成安装期脚本风险。对应地，`scripts/verify-manifest.mjs` 的 R4 判据从「禁止 install/prepare/prepublish 类脚本」精确化为「禁止安装期脚本，`prepublishOnly` 除外」。

#### 17.2.1 第 3 条从「tag 等于 HEAD」改为「进包内容未变」（0.3.4 之后）

原判据要求 tag 精确指向 `HEAD`。它的问题是把「包可发布」和「发布就绪」混为一谈：任何不进包的提交（`docs/`、`scripts/`、`.github/`、`package-lock.json`）都会让 `HEAD` 越过 tag，于是 `npm test` 里的 R16（`npm publish --dry-run` → `prepublishOnly`）从提交那一刻起一直红到下一次发版。当时的变通是「每次都升版本」，代价是发出一个内容完全相同的版本号——0.3.1（只改 README）、0.3.3（只加 CHANGELOG）都是这么来的。

真正的铁律是「npm 上发布的内容 == tag 指向的内容」。所以判据改为比对 `package.json` + `files` 白名单内文件在 `tag..HEAD` 之间的差异：

- 差集为空（含 tag 正好指向 `HEAD` 的严格情形）→ 放行；
- 有进包文件变化 → 失败，提示「进包内容变了就必须升版本、重新打 tag」。

反向验证：`git diff --name-only v0.3.3 v0.3.4 -- <白名单>` 检出 `CHANGELOG.md`、`package.json`（真实的进包变化会被拦住）；`v0.3.4..HEAD` 为空（纯 CI 提交放行）。这次改动本身（只动 `scripts/verify-release.mjs`、`AGENTS.md`、`docs/`）不进包，因此没有升版本。

### 17.3 历史遗留豁免

`0.0.0-stage` 发布于铁律生效之前，GitHub 侧从未打过 tag，已无法追溯。`scripts/verify-release.mjs` 用 `LEGACY_VERSIONS` 白名单豁免它，并打印一行「历史遗留，豁免」。该白名单只允许加入铁律生效前的版本，新版本一律不得豁免。

| 用 `systemPrompt.context` 替代 section | 宿主 `RuntimeContextProjection.project` 有 `if (this.retained?.text === snapshot) return;` 去重，文本不变就不发新消息，「每步重申」做不到；且会失去「不受 `includeRuntimeContext` 抑制」这一优势 |
| `optionalRequire` 吞掉全部异常 | 我方 `require('react')` 直接 fail-fast 更好；吞异常会让镜像断言变成空跑 |

## 二十一、0.3.4 变更：显示名表校验 + 真容器卸载验证

### 21.1 为什么发这一版

两项来自 `dsh-thinking-language` 对比评审的遗留改进（评审结论里列为 P1 / P2），都不是用户可见的 bug，但都是**判据缺口**：

1. **显示名表零判据。** `client.js` 的 `LANGUAGE_NAMES` 与 `lib/text.js` 的 `LANGUAGE_NAMES` 是两份手抄副本。`scripts/verify-mirror.mjs`（清单 M14）的镜像段终点刻意停在 `/** 语言标签 → 显示名` 之前——那张表不属于「解析规则」，此前完全没人比对。表一旦分叉，面板显示「日本語」而实际注入别的语言，用户看不出来，也没有任何脚本会红。
2. **卸载语义零覆盖。** 74 项验收清单全是 grep / 正则，8 项客户端验证只测浏览器半。对「插件卸载后 section / 事件监听有没有残留」一条判据都没有。竞品 `cordis-check.mjs` 用真 `@deepseek-ai/cordis` 容器测这个，我们照做。

### 21.2 改动内容

**P1：`scripts/verify-mirror.mjs` 增加显示名表比对**

- 新增抽取边界 `TABLE_START_MARK = 'const LANGUAGE_NAMES = ['`（client 与 host 两侧同一字面量，同一个 `loadTable()` 通吃）与 `LABEL_START_MARK = 'function languageLabel(code) {'`；`languageLabel` 的结束用 `/** 极简` 标记。
- 两条判据并轨：
  - **表结构**：`JSON.stringify` 逐对比较，键缺失 / 多出 / 顺序或显示名不同都会报出具体差异。
  - **行为**：`LABEL_CODES` 共 32 组（两张表全部 key + 大写变体 + `${key}-x` 变体 + 空格包裹 + 脏值 `null` / `undefined` / `0` / `{}` / `[]`），逐组比 `hostLanguageLabel(code)` 与 `clientMod.languageLabel(code)`。
- 为什么不只做行为比对：行为能覆盖「改错 label」，但发现不了「某一侧偷偷多一条键」——那条键在行为矩阵里可能永远不被调用。反过来只比表结构也不行：`languageLabel` 的前缀匹配逻辑（`lower.startsWith(key + '-')`）与空值兜底（返回「简体中文」）比表本身更容易改坏。
- 反向验证：篡改 `client.js` 的 `['ja', '日本語']` → `['ja', '日语']`，脚本报 4 处差异并 `EXIT=1`；恢复后 `EXIT=0`。
- 陷阱记录：`| tail -8` 会让 `$?` 取到 `tail` 的退出码，看起来「篡改后仍 EXIT=0」。判退出码必须不带管道，或看 `${PIPESTATUS[0]}`。

**P2：新增 `scripts/verify-dispose.mjs`（真容器卸载验证）**

- 用真 `@deepseek-ai/cordis` 的 `Context` 起容器，`Service` 子类伪造 `systemPrompt` 与 `commands` 服务。
- 7 项用例：
  1. apply 后注册 `language-guard:head` / `:mid` / `:tail` 三段，order 分别为 `-2000` / `5100` / `11200`；
  2. `dispose()` 后三段全部释放；
  3. D 档挂载后 `agent/pre-step` 恰有 1 个监听，卸载后归零（通过 `ctx.events._hooks` 数，取不到则判失败并提示更新脚本——不允许静默跳过）；
  4. B 档 mid 的 `text()` 为空串，C 档非空（对照，防「所有档都返回空串」这种反向 bug）；
  5. 有 `commands` 服务时 `/language` 注册成功，卸载后释放；
  6. 缺 `settings` 服务时 apply 正常完成、三段照常注册（headless 部署的关键行为）；
  7. 重复挂载/卸载两轮不累积残留。
- 反向验证：把 `FakeSystemPrompt.section()` 返回的释放函数改成空函数 → 用例 2、7 变红，`EXIT=1`；恢复后 `EXIT=0`。

## 二十二、0.3.5 变更：适配 dsh 0.2.1-rc.3，宿主 API 自检可重复运行

### 22.1 这次改动的性质

不是修 bug，也不是加功能，而是**把一次性的适配动作变成可重复的判据**。

背景：本插件依赖一批宿主私有接口——`systemPrompt.section/context`、`settings.configure/describe`、`commands.register`、`agent/pre-step`，以及客户端的 `configForms`、`locale` 与两个 slot 名。这些都不在公开 API 文档里，dsh 每次升级都可能改名或改签名，而改完之后插件是**静默失效**的（section 还在注册，但宿主不再调用；面板还在渲染，但读不到配置）。此前每次升级都靠人工读 asar、逐个 grep，既不可重复，也无法在 CI 里跑。

### 22.2 新增 `scripts/verify-host-api.mjs`

直接解析 DSH 桌面版的 `app.asar`（Electron asar 格式：前 16 字节含 header pickle 大小与 JSON 长度，数据段起点 = 8 + headerSize），把宿主源码读成字符串，逐条断言本插件实际用到的 23 个接口仍在、且签名关键片段没变。

23 项覆盖：

| 分组 | 断言内容 |
|---|---|
| 版本 | 宿主 `dsh/package.json` 的 version 不低于 `engines.dsh` 下限 |
| 注入通道 | `systemPrompt.section()` / `context()` 存在；`section` 仍要求 `order` 为有限数 |
| 渲染语义 | `renderPrompt` 仍 `filter((text) => text.length > 0)`（B 档 mid 返回 `""` 等价于该段不存在）；`interpolate: false` 仍受支持；`TOOLS_SDK` 仍为 `5000`（mid 段 order `5100` 的定位依据） |
| 设置 | `settings.configure()` / `describe()` 存在；`settings/document-updated` 仍会发出（UI 语言缓存靠它刷新）；describe 行仍含 `ns` 与 `value`；`volatileForm` 仍按 `schema.meta.volatile` 判定 |
| 命令与事件 | `commands.register()`；`agent/pre-step`；`dsh-llm` 的 `createUserMessage` |
| 客户端 | `configForms` 服务及其 `get(entryId)` / `whileServed(namespaces, register)`；`locale.register(ns, ...)` / `bind(ns)`；`LOCALE_IDS` 仍是 `["zh","en"]`；slot `sidebar.footer.action` 与 `plugins.bundle.config` |

只做「符号还在不在」的断言，不做语义分析——这是升级时最先被破坏的东西，也是最容易机械判定的。

### 22.3 为什么找不到 asar 时跳过而不是失败

CI 上没装 DSH 桌面版，`app.asar` 不存在是正常情况。脚本打印 `SKIP` 并 `exit 0`。代价明确：这条判据在 CI 上不生效，只有装了桌面版的机器（也就是真正要升级的机器）才跑得起来。这与 `verify-dispose.mjs` 在缺 cordis 时跳过的处理是同一套取舍。
