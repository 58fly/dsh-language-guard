## 一、分发方式：为什么是 GitHub 而不是 npm

npm 发布被放弃，不是配置问题，是**当前出口 IP 被 Cloudflare 风控**。实测证据：

| 检查项 | 结果 | 含义 |
| --- | --- | --- |
| `https://www.npmjs.com/signup` | **403**，响应体 `<title>Just a moment...</title>` | Cloudflare 人机验证页 |
| `https://www.npmjs.com/` | 403 | 全站拦截，不只是注册页 |
| `https://www.npmjs.com/login` | 403 | 登录页同样被拦 |
| 直连真实 Cloudflare IP + `--noproxy '*'` | **仍 403** | 排除本地 DNS / 代理干扰 |
| `registry.npmjs.org/-/ping` | **200** | 发布通道本身正常 |
| `npm ping` | `PONG 784ms` | registry 可达 |
| `npm adduser --auth-type=legacy` | `Account creation via legacy auth is unavailable` | 命令行注册已被 npm 关闭 |
| `npm adduser --auth-type=web` | 只给一个仍需浏览器的登录链接 | 注册必须过网页 |

结论：**注册账号必须过浏览器，而浏览器被 Cloudflare 拦住；命令行注册通道已被 npm 关闭。** 换网络（手机热点、换机场节点）可以解决，但这不是代码问题。

GitHub 侧的通道完全正常，且 DSH 插件管理器原生支持 Git 地址，所以改用 GitHub 分发，功能上没有任何损失。

## 二·补、本机 profile 的一个既有障碍及修复（与本插件无关，但会挡住安装）

排查 `pnpm add` 失败时发现：本机 desktop profile 的 **`pnpm install` / `pnpm add` 全部失败**，报

```
[ERR_PNPM_INVALID_VERSION_UNION] Invalid versions union.
Found: "@dsh-external/dsh-super-injector@git+https://github.com/yjh051108/dsh-routing-suite.git".
Use exact versions only.
```

**根因**：`pnpm-workspace.yaml` 的 `allowBuilds` 段里有三条 `@dsh-external/dsh-super-injector` 键，其中两条的 key 是 Git spec 而不是精确版本：

```yaml
allowBuilds:
  '@dsh-external/dsh-super-injector': true                                                    # ← 有效
  '@dsh-external/dsh-super-injector@git+https://github.com/yjh051108/dsh-routing-suite.git': true   # ← 无效
  '@dsh-external/dsh-super-injector@https://codeload.github.com/yjh051108/dsh-routing-suite/tar.gz/1952733…': true  # ← 无效
  '@google/genai': true
  protobufjs: true
```

这是 `@dsh-external/dsh-super-injector`（第三方注入器）留下的记录——它自己的 `patches/repair-super-injector.mjs` 注释里就写了「该依赖的版本是 git tarball URL，pnpm 会报 `ERR_PNPM_INVALID_VERSION_UNION` 并让 `pnpm install` 直接失败」。pnpm 11 在解析 `allowBuilds` 的 key 时会做版本联合校验，遇到 git spec 即中止整个安装。

**注意**：`node_modules/.modules.yaml` 里也有一份同样的 `allowBuilds`，但那是 pnpm 的缓存投影，**改它无效**——pnpm 以 `pnpm-workspace.yaml` 为准。第一次修错位置（只改了 `.modules.yaml`）时现象完全不变。

**修复**：只删掉 `pnpm-workspace.yaml` 里那两条带 Git spec 的键，保留按包名的那条（`'@dsh-external/dsh-super-injector': true` 仍然允许它跑构建脚本）。

```bash
cd ~/.dsh/profiles/desktop
cp pnpm-workspace.yaml pnpm-workspace.yaml.bak-$(date +%s)
python3 - <<'EOF'
import io
p = 'pnpm-workspace.yaml'
s = io.open(p, encoding='utf-8').read()
for bad in [
    "  '@dsh-external/dsh-super-injector@git+https://github.com/yjh051108/dsh-routing-suite.git': true\n",
    "  '@dsh-external/dsh-super-injector@https://codeload.github.com/yjh051108/dsh-routing-suite/tar.gz/195273352f23bff7f9023ebe2ec0cdbdf9c98f10': true\n",
]:
    s = s.replace(bad, '')
io.open(p, 'w', encoding='utf-8').write(s)
EOF
pnpm install --lockfile-only     # 退出码 0 即修复
```

**修复后实测**：`pnpm install --lockfile-only` 从「退出码 1 + INVALID_VERSION_UNION」变为「退出码 0，`Done in 4s`」，且 lock 正确写入本插件的 Git 来源：

```yaml
dsh-language-guard:
  specifier: git+https://github.com/58fly/dsh-language-guard.git
  version: https://codeload.github.com/58fly/dsh-language-guard/tar.gz/9ee56fa40811bf1b6d12d8e8df1a7472bccf9c57(@deepseek-ai/schemastery@3.18.5)
```

> 这个修复只影响 pnpm 的构建脚本白名单，不改任何已安装包。若 `@dsh-external/dsh-super-injector` 日后重装并再次写入带 Git spec 的键，需重做一次。

## 十一、0.1.1 变更：约束文本压过 AGENTS.md 一类语言约定

### 问题现象

用户把目标语言切成 `ja`（日本語）后报告「没有任何改变」。

### 排查结论（三段事实，逐条可复现）

1. **配置确实生效了**：`cordis.patch.yml` 里是 `targetLanguage: ja`；解压会话日志读 `system/message`，最新节点的 head 段确实是「一律使用日本語（语言代码 ja）」，三段 3/3、落点递增。Host 侧注入链路没有问题。
2. **改配置本来就不需要重启**：写入走 `dsh-config-editor`（README：「保存到当前 profile 的 patch 并立即应用」），volatile 字段经 `cordis-plugin-loader` 的 `_commitVolatile` → `loader/volatile-update` 只替换运行中的引用、不重挂插件；system prompt 每次请求重新装配。所以「必须重启」这个猜测不成立。
3. **真正的原因是约束文本压不住中文写成的 AGENTS.md**：0.1.0 的首段只声明「优先于后续任何**英文**内容」。而用户的全局 `~/.dsh/AGENTS.md` 里写着「默认所有对话……都必须使用简体中文」，这是**中文**写成的硬约束，经 `agent-instructions` 以 user 消息注入，落在首段之后。模型据此继续用中文 → 用户看到「选了日语没变化」。

### 0.1.1 的两处修改

| 改动 | 位置 | 效果 |
|---|---|---|
| 首段新增两段：优先于本 system prompt 其余全部内容；优先于**任何**语言类约定（AGENTS.md / CLAUDE.md / .cursorrules / 用户偏好与长期记忆 / 项目规范 / 团队约定 / 技能模板），不论用哪种语言书写、经哪个通道送达 | `lib/text.js` 的 `HEAD_INTRO` | 与中文 AGENTS.md 冲突时以插件为准 |

## 十三、0.2.0 变更：自动语言模式

### 为什么加

0.1.x 只有一个 `targetLanguage` 字段，装完默认 `zh-CN`。这带来两个实际问题：

1. **界面语言是英文的用户**（或想在英日韩之间切换的用户）每次都要手动改配置，忘了改就一直是中文；
2. 插件本身是**通用语言锁定器**（`01-mechanism.md` 的定位：目标语言可配，默认简体中文），但 0.1.x 的默认值把「默认」和「唯一常用值」混在一起，用户看不出它其实是可跟随的。

0.2.0 引入**语言模式**：`自动`（跟随 DSH 界面语言）与 `手动`（固定使用配置的语言）。默认行为对中文用户完全不变——界面语言是中文时自动解析为 `zh-CN`。

### 一个必须先说清的边界：不读系统语言

「自动」指的是**跟随 DSH 的界面语言**，不是跟随操作系统语言。这不是偷懒，是两条路都走不通：

| 方案 | 实测结论 | 结论 |
| --- | --- | --- |
| 读 Electron 的 `app.getLocale()` | Host 进程以 `ELECTRON_RUN_AS_NODE=1` 运行，`require("electron")` 抛 `Cannot find module 'electron'` | 不可达 |
| 读 Node 的 `Intl.DateTimeFormat().resolvedOptions().locale` | 在该进程里**恒为 `en-US`**，而本机系统实际是 `zh-Hans-CN` | 会把中文用户误判成英文，比不判断更糟 |
| 读 DSH 自己的界面语言偏好（`settings.describe()` 里 `ns === 'locale'` 的 `preference`） | 与官方 `/lib/main.js` 读取界面语言的方式一致，可用 | **采用** |

因此：**任何文档、任何界面文案都不得声称插件会识别系统语言**。这条已写进 `docs/验收清单.md` 的 M 组与 README 的已知限制。

### 配置与升级兼容性

`languageMode` 的 schema 默认值是**空串 `''`**，不是 `'auto'`：

```js
languageMode: z.union([z.const(''), z.const('auto'), z.const('manual')]).default('').volatile()
```

空串是**三态哨兵**，语义是「用户从没设置过」。只有空串才能区分「用户显式选了自动」和「用户没动过」——后者必须再看 `targetLanguage` 是否被改过，否则 0.1.x 老用户手选的 `ja` 会被界面语言静默覆盖。

由此得到的升级行为（与 README「从 0.1.x 升级」一节一致）：

| 0.1.x 的 `targetLanguage` | 升级后模式 | 结果 |
| --- | --- | --- |
| 保持默认 `zh-CN` | 自动 | 界面语言中文 → `zh-CN`；界面语言英文 → `en` |
| 改成 `ja` / `en` / `zh-TW` 等 | 手动 | 保留原值，不被界面语言覆盖 |

映射规则只有 4 条（`lib/language.js` 的 `mapPreference`）：`zh` 开头的标签 → `zh-CN`、`en` 开头的标签 → `en`、`ja` / `ko` / 其他合法 BCP-47（外部语言包 id）原样透传、缺失 / 空 / 非法 → 回落 `targetLanguage`（默认 `zh-CN`）。**不做简繁细分**：DSH 内置界面语言只有 `zh` 与 `en`（`dsh-client-locale/lib/index.js:11` `LOCALE_IDS = ["zh","en"]`），需要繁体请切手动选 `zh-TW`。

### 本版新增的验收判据

`docs/验收清单.md` 新增「三、自动语言模式验收清单（M 组）」共 13 条，全部可在 `scripts/verify-checklist.sh` 里机械判定：
