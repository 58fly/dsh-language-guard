# 调研：自动识别语言环境的信号来源与 BCP-47 映射规则

## Question

插件目前要用户**手动**选目标语言（侧栏快速切换 / 设置页 chip / 自定义文本框）。用户要求新增：**自动识别当前语言环境，语言模式自动选择**。

用户已在澄清中定案三点：

1. **识别信号**：界面语言为主，系统语言兜底。
2. **自动决定的对象**：只自动选**目标语言**（不自动选三档强度）。
3. **自动与手动的关系**：**自动 / 手动两态，默认自动**。选自动时跟随环境；选具体语言时固定不变；侧栏菜单里两项都能看到当前处于哪种。

## 需要查清的事实

### 一、Host 半身如何拿到「界面语言」

Client 侧 `ctx.locale.getSnapshot().active` 是**最终生效**的语言（含浏览器派生、外部语言包），但它在浏览器侧；本插件的三段 system prompt 文本由 **Host** 生成，Host 必须自己拿到这个值。

待核实的三条候选路径：

- **A. 读 `settings.describe()` 里的 `locale` 命名空间**。`dsh-client-locale/lib/index.js` 的 `Config = z.object({ preference: ...volatile() })`、`LOCALE_SETTINGS_NAMESPACE = "locale"`、`LOCALE_FIELD = "preference"`；而 `SettingsForms#describe()`（`dsh-settings/lib/index.js:411-455`）会遍历所有**有 volatile 字段**的 entry 并返回 `{ ns, value, ... }`。→ 需确认跨插件读别人命名空间是否被允许、`preference` 缺失时的行为。
- **B. Client 把自己的 `active` 写回本插件 config**（新增 volatile 字段 `detectedLanguage`，Client 在挂载与 `locale/change` 时 `form.set`）。→ 需确认写入是否会污染 `cordis.patch.yml`、频率与副作用。
- **C. 纯 OS 语言兜底**（Host 进程 `Intl.DateTimeFormat().resolvedOptions().locale` 或 `process.env.LC_ALL/LANG`）。→ 需确认 Electron 主进程里的实际返回值。

### 二、界面语言到 BCP-47 的映射

**这是关键坑**：`dsh-client-locale/lib/index.js` 的 `LOCALE_IDS = ["zh", "en"]` —— 内置界面语言只有 `zh` 和 `en`，`zh` **不区分简繁**。而本插件的 `targetLanguage` 是 BCP-47（`zh-CN` / `zh-TW` / `en` / `ja` / `ko` / 任意合法标签）。

故必须定一套映射规则，至少覆盖：

- `zh` → ？ （`zh-CN` 还是 `zh-TW`，是否需要看 OS 地区来细分）
- `en` → `en`
- 外部语言包 id（如 `ja`、`ko`，由 `ctx.locale.addLanguage` 注册）→ 原样使用
- OS 语言标签（`zh-Hans-CN`、`zh-Hant-TW`、`ja-JP`、`en-US`）→ 需要归一化到本插件预设的粒度，还是原样透传

### 三、与现有 6 个配置字段的关系

现有 `targetLanguage`（默认 `zh-CN`）是手动值。新增自动模式后，`targetLanguage` 与新模式字段如何共存：

- 方案甲：新增 `languageMode: 'auto' | 'manual'`，`targetLanguage` 仅在 manual 下生效（auto 下界面显示解析结果但不可编辑）
- 方案乙：`targetLanguage` 允许特殊值 `'auto'`，但会破坏 BCP-47 正则与现有校验
- 方案丙：新增 `autoDetect: boolean`，与 `targetLanguage` 并列

需给出定案与理由，并明确**侧栏菜单与设置卡片在 auto 态下怎么显示**（要让人一眼看出「现在是自动，当前解析成日语」，而不是像 0.1.0 那样「点了没反应」）。

## 约束

- 遵守官方 `practices.md`：不得监听 `system-prompt/assemble` 增删文本；改写 waterfall 必须 `await next()` 且 spread。

- 必须能解释清楚「为什么现在这个语言」，不能让用户猜。

### A. 三条候选路径的实测对比

| 维度 | **A**：`settings.describe()` 读 locale ns | **B**：Client 回写 `detectedLanguage` | **C**：OS 语言 |
|---|---|---|---|
| Host 能否拿到 | ✅ 能（`ctx.inject(["settings"])`） | ✅ 能（读自己 config） | ❌ 不能（`Intl` 恒为 `en-US`） |
| 是否反映界面语言 | 部分：只反映**用户显式选过**的值 | ✅ 完全：就是 `getSnapshot().active` | ❌ 完全不反映 |
| `preference` 缺失时 | 读不到（`value === {}`） | ✅ 仍能拿到浏览器派生值 | ❌ 永远 `en-US` |
| 外部语言包 | ✅ 若 preference 指向它 | ✅ 一定拿到 | ❌ |
| 写盘 | ❌ 不写 | ⚠️ 每次变化写一次 `cordis.patch.yml`（**检测值变持久值**） | ❌ 不写 |
| 单次开销 | ≈ 2–5 ms（**必须缓存 + 门控**） | 读自己的 volatile 引用，≈ 0 | ≈ 0 |
| 感知变化 | `settings/document-updated`（`api-catalog.js:4395-4402`） | 自己的 config volatile 引用 | 无（进程环境不变） |
| 合规性 | ✅ 官方主进程同款做法（`main.js:8927-8931`） | ✅ 与官方 `setLocale` 同量级写盘，但有语义副作用 | ❌ 数据源错误 |

**定案：A 为主、B 为可选增强且默认关闭、C 弃用。**

判定链（Host 侧）：

```
uiLocale = 1. settings.describe() → ns==="locale" → value.preference（存在且非空）
         → 2. 本插件 config 的 detectedLanguage（Client 回写；可选，默认关闭时跳过）
         → 3. targetLanguage 配置值（默认 "zh-CN"）—— 不编造假信号
```

### B. 路径 A：源码证据与两个硬限制

**为什么合规**：`SettingsForms#describe()`（`dsh-settings/lib/index.js:413-464`）只按两条筛 entry —— `:417` `entry.fiber.state === 2`（激活态）、`:418-419` `volatileForm(schema) !== undefined`（有 volatile 字段）。**不检查调用者身份，没有 ACL、没有 scope 校验、没有白名单**。

`SettingsForms` 本身是 Host Service（`:322-330` `class extends Service` + `super(ownerContext, "settings")`），任何 Host 插件 `ctx.inject(["settings"])` 即可拿到。

**读接口只有 `describe()` 一个**（captain 复核 `/tmp/settings.js` 全类方法：`configure` / `invalidate` / `prepareDocument` / `describe` / `update` / `replace` / `mutate` / `write` / `schema`）—— **没有 `read(ns)` / `get(ns)`**，`describe(options)` 的 `options` 只有 `redactSecrets`，**不能按 ns 过滤**，必须拿全量再自己 `find`。

**官方先例**（决定性证据）：`/lib/main.js:8927-8931` 就是主进程按 `item.ns === "locale"` 找行、取 `value.preference`、缺失时 `?? null`：

```js
const localePreference = (namespaces) => {
  const locale = namespaces.find((item) => record$3(item) && item.ns === "locale");
  if (!record$3(locale) || !record$3(locale.value) || locale.value.preference !== void 0 && typeof locale.value.preference !== "string") throw new Error("desktop welcome: invalid locale preference");
  return locale.value.preference ?? null;
};
```

`preference` 缺失时 `value` 的形状（用 asar 内真 `schemastery@3.18.5` + 逐行照抄 `dsh-settings` 的 `volatileForm`/`projectForm`/`plainConfig`/`plainSchema` 实测）：

| 配置 | describe 行 | `value.preference` |
|---|---|---|
| 未设置 | `{"ns":"locale","value":{}}` | `undefined`（`value` 是 `{}`，**不是** `undefined`/`null`） |
| `"zh"` | `{"ns":"locale","value":{"preference":"zh"}}` | `"zh"` |
| `"ja"` | `{"ns":"locale","value":{"preference":"ja"}}` | `"ja"` |

本机 `~/.dsh/profiles/desktop/cordis.patch.yml` 第 4-7 行即 `- id: locale` / `name: "@deepseek-ai/dsh-client-locale"` / `config: { preference: zh }` → **entry id 确实是 `locale`**，本机能直接读到 `"zh"`。

**硬限制 1：`preference` 缺失时读不到。** 此时 Client 的 `active` 是 `provisional`（`dsh-client-locale/lib/client.js:1343-1346 resolveActive()` 在 `preference === undefined` 时返回 `this.provisional`），而 `provisional` 来自 `detectBrowserLocale`（`:1476-1489`，遍历 `navigator.languages`）。**这个值 Host 侧完全不可见。**

**硬限制 2：`describe()` 不能每 step 调。** 它每次都走 `configEditor.configuration()` → `loadProfileDirectory()`（`dsh-app-boot/lib/index.js:1015-1051`），全部是同步 `readFileSync`（`:905-909`、`:3961-3968`）。本机实测：bundles 22、filesRead 36、totalBytes 96378、**0.793 ms/次**（仅读盘）+ **1.173 ms**（schema 投影，20 entry × 12 字段）≈ **2–5 ms/次**。而 `assemble()` 每 step 一次（`dsh-agent-loop/lib/index.js:907`）。→ **必须缓存 + 事件驱动 + manual 态门控**。

**感知变化**：监听 `settings/document-updated`（`dsh-tool-cordis/lib/types/api-catalog.js:4395-4402`，签名 `(ns: SettingsNamespace, revision: number): void`），emit 点在 `dsh-settings/lib/index.js:435` 与 `:461`。**重复调 `describe()` 不会引发事件风暴**：emit 受 `previous?.raw !== raw || previous.autoGenerate !== autoGenerate` 保护，而 `raw = JSON.stringify([fiber.uid, schema.toJSON(), entry.options.config ?? {}])` 是稳定值 —— 正常重复调用不 emit，不会自触发死循环。

**门控要求（写进实现）**：`describe()` 只在 `languageMode !== 'manual'` 时调用。manual 态用户已明确指定语言，读 describe 纯属浪费；从 manual 切回 auto 时由 `settings/document-updated`（ns = `language-guard`）触发一次刷新，无需轮询。

### C. 路径 B：写盘代价与「检测值变持久值」的语义代价

**每次 `form.set()` 的完整链路**：

1. Client `ConfigForm.set`（`dsh-client-ui-settings/lib/client.js:1140-1146`）→ `mutate`（`:1165-1182`）→ `ctx.remote.settings.mutate(...)` 跨网络 RPC。
2. Host `dsh-settings/lib/index.js:470-473 update()` → `:501-537 write()`（volatile 校验）→ `configEditor.edit()`。
3. `dsh-config-editor/lib/index.js:69-135`：文件锁（`:72`）→ `readProfilePatches`（`:74`）→ `reconcileProfilePatches`（`:75`）→ `readFile(path)`（`:86`）→ `parseDocument`（`:91`）→ `document.setIn([index,"config"], ...)`（`:110`）→ `writeFileAtomic(path, String(document), {mode:384})`（`:123`）→ 再次 `reconcileProfilePatches`（`:125`），失败回滚（`:127`）→ 全程 `hmr.runExclusive`（`:133-134`）。
4. `:24-26` 明确 `documentPath = profileContext.patchPath` —— **写的就是 `~/.dsh/profiles/desktop/cordis.patch.yml` 本身**。

→ **每次写 = 一次完整的「文件锁 → 读 96 KB / 36 文件 → 改 YAML AST → 原子写盘 → reconcile」往返，改的是用户手写的配置文件。**

**频率本身不是新风险**：官方 locale 插件自己就在写同一个文件 —— `dsh-client-locale/lib/client.js:1278-1284 setLocale()` 末尾 `this.host?.set(LOCALE_PREFERENCE_FIELD, match.id)`，且注释 `:1269-1275` 明说「即使 id 已与生效 locale 相同也会持久化」。

**但语义代价是新的，这才是关键**：把「检测结果」写进 `cordis.patch.yml`，等于把**一次环境观测**变成**用户的持久偏好**。三个后果：

1. **检测值伪装成用户意图。** 用户从没选过 `ja`，只因某天界面语言是 `ja`，配置里就永久留下 `detectedLanguage: ja`；之后即使界面切回中文，只要 `preference` 缺失，判定链就会读到这条陈旧值。
2. **多端共享同一个 home 会互相覆盖。** `cordis.patch.yml` 是**按 profile 而非按设备/会话**的：Desktop 与 Web、两台机器共用 `~/.dsh` 时写同一份文件。A 端 `zh`、B 端 `en` 会反复覆写对方，且每次覆写都是一次完整写盘。
3. **写盘链路有成本与失败面。** 任一步失败都要回滚（`dsh-config-editor/lib/index.js:127`）。

**有没有「不落盘」的 Client → Host 通道？查过，都不合适**：

- **session command**（官方唯一承认的 Client-callable Host entry point，`references/user-actions.md`：「The UI action calls it through a Client-callable Host entry point found with inspection, such as a session command that `ctx.remote.commands.execute()` runs」）：`ctx.remote.commands.execute(sessionId, line, attachments)` 会 **durably log `command/run` / `command/done`，并在每个标签页渲染成 persistent flow node**（`/dsh/node_modules/@deepseek-ai/dsh-client-ui-commands/lib/client.js:1706-1725` 注释原文：「the host executor durably logged the lifecycle (`command/run`/`command/done`) and the outcome renders as a persistent flow node」）。用命令传高频环境观测会把用户时间线塞满命令记录 —— **不可接受**。
- **自定义 RPC**：官方文档没把「插件自建 Client↔Host RPC」列为支持路径（`user-actions.md` 只承认 session command 与 agent tool 两种入口）。依赖它等于赌内部实现。

**定案：路径 B 保留为可选增强，但默认关闭。** 启用时必须满足三条：(1) 只在 `active !== prev` 时写；(2) UI 明确标注该值是**检测值**，不参与 manual 态；(3) 文档写明多端共享 home 会互相覆盖。

```js
const prev = form.getSnapshot()?.value?.detectedLanguage;
if (active === prev) return;            // 值不变就不写盘
form.set('detectedLanguage', active);
```

**路径 B 的唯一价值**：拿到真正生效的 `active`，覆盖 A 拿不到的两种情况 —— (1) `preference` 从未设置；(2) `preference` 指向未注册的外部语言包 id（`resolveActive` 回落到 `provisional`，`:1343-1346`）。

**推荐**：既然路径 A 在本机已能拿到 `zh`，**先只做 A**；把 B 作为后续 issue，等真的出现「`preference` 从未设置」的用户反馈再补。

### D. 路径 C：Host 侧没有可靠的系统语言信号

**先确认 Host 到底在不在 Electron 进程里 —— 在。** 进程树（captain 用 `ps` 实测；本会话沙箱禁止执行 `ps`，报 `bash: /bin/ps: Operation not permitted`，故引用其观测）：

```
42989  /Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness              ← Electron 主进程
43665  └─ 同上二进制 --expose-internals .../dsh-desktop-host/lib/index.js .../profiles/desktop   ← 我们的 Host
42992  Helper --type=utility --lang=en-US
43003  Helper (Renderer) --lang=en-US
```

**但「在 Electron 二进制里」不等于「能用 Electron API」。** 实测（与 Host 完全同一启动方式，`/lib/main.js:3791-3811` spawn + `desktopNodeEnvironment`（`:3649-3658`）注入 `ELECTRON_RUN_AS_NODE: "1"`）：

```
$ ELECTRON_RUN_AS_NODE=1 "/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" -e '...'
{
  "versions_electron": "44.7.0",          ← 确实是 Electron 二进制
  "process_type": "(undefined)",           ← 既不是 main 也不是 renderer，是纯 Node 模式
  "electronRunAsNode": "1",
  "LANG": "C.UTF-8",
  "require_electron": "FAIL: Cannot find module 'electron'",
  "resolved": "FAIL: MODULE_NOT_FOUND"
}
```

进一步用内部 binding 探测（Host 启动时带 `--expose-internals`，该探测在 Host 里同样成立）：

```
electron_common_app        → FAIL: No such module: electron_common_app
electron_common_app_bundle → FAIL: No such module: electron_common_app_bundle
electron_browser_app       → FAIL: No such module: electron_browser_app
electron_common_v8_util    → OK        ← 只有通用 v8 工具，与 app/locale 无关
```

→ **`ELECTRON_RUN_AS_NODE=1` 下 Electron 的 app 模块整个不注册**，`app.getLocale()` / `app.getPreferredSystemLanguages()` 完全不可达。

**asar 内谁引用 electron**：全库 grep `from "electron"` / `require("electron")` / `app.getLocale`，命中只有 `/lib/main.js`、`/lib/preload-app.cjs`、`/lib/preload-mandatory.cjs`、`/lib/preload-platform-account.cjs` 与第三方 `node_modules/electron-updater/*`。**没有任何 `dsh/*` 包引用 electron**；`dsh-desktop-host/lib/index.js` 不 import 它、不暴露任何 locale 能力（captain grep `locale`/`Locale`/`app.getLocale` 零命中，本节复核一致）。主进程只把 `systemLanguages` 塞进 `localeBootstrap` 给 **renderer**（`/lib/main.js:12499-12506`），Host 与主进程之间只有 `dsh-desktop-host` 自己的控制协议（`/lib/main.js:3818-3837` 处理 `ready`/`shutdown`/`fatal`），没有语言查询。

**`Intl` / `LANG` 也不可信**（实测，Electron 44.7.0 与 Host 同运行时）：

| 场景 | `Intl.DateTimeFormat().resolvedOptions().locale` |
|---|---|
| 本机 Host 环境（`LANG=C.UTF-8`，裸 node） | **`en-US`** |
| `env -u LANG -u LC_ALL -u LC_MESSAGES -u LANGUAGE node` | `en-US` |
| **`ELECTRON_RUN_AS_NODE=1 ".../DeepSeek Harness" -e '...'`** | **`en-US`** |
| 同上 + `LANG=zh_CN.UTF-8 LC_ALL=zh_CN.UTF-8` | `zh-CN` |
| 同上 + `LANG=ja_JP.UTF-8` | `ja-JP` |

**而 macOS 的真实系统语言是 `zh-Hans-CN`**：`defaults read -g AppleLanguages` → `("zh-Hans-CN")`；`defaults read -g AppleLocale` → `zh_CN`；Swift Foundation（Electron 同源）→ `Locale.preferredLanguages = ["zh-Hans-CN"]`、`Locale.current.language.maximalIdentifier = zh-Hans-CN`。

→ **`Intl` 只看 `LANG` 环境变量，完全不看 NSLocale。Host 进程 `LANG=C.UTF-8` → 永远 `en-US`，即使系统语言是中文。这会把中文用户误判成英文，比没有信号更糟。**

**四条路逐一实测，全部不可用**：

| 候选 | 实测结果 | 判定 |
|---|---|---|
| `Intl.DateTimeFormat().resolvedOptions().locale` | `en-US`（系统语言实为 `zh-Hans-CN`） | ❌ 会误判，**比没有更糟** |
| `process.env.LANG` / `LC_ALL` | `LANG=C.UTF-8`、`LC_ALL` 未设 | ❌ 同上 |
| `require("electron")` → `app.getLocale()` | `MODULE_NOT_FOUND`；内部 binding `No such module` | ❌ 不可达 |
| `defaults read -g AppleLocale`（spawn 子进程） | 能拿到 `zh_CN`，但 macOS 专属、需 spawn、Windows/Linux 无此命令 | ❌ 跨平台不可用，不值得为兜底引入平台分支 |
| `dsh-desktop-host` 自带能力 | 不 import electron，不暴露 locale | ❌ 不存在 |

**结论：Host 侧没有可靠的系统语言信号。不要硬编一个假信号。** 兜底退化为 `targetLanguage` 配置值（默认 `zh-CN`）。**弃用路径 C。**

> 注意「系统语言」在本方案里仍有用途，但**只在 Client 侧**：用于细分 `zh` 的简繁（见 E 节）。Client 经 `__DSH_LOCALE__` IPC 从主进程拿 `app.getPreferredSystemLanguages()`（`/lib/main.js:12077`、`:12499-12506`）或 `navigator.languages`。这与「Host 侧没有系统语言信号」并不矛盾 —— 数据只在 Client 可达。

### E. 界面语言 → BCP-47 映射规则

**核心矛盾**：`LOCALE_IDS = ["zh", "en"]`（`dsh-client-locale/lib/index.js:11`、`lib/client.js:922`），`zh` 不区分简繁；而 `targetLanguage` 需要 `zh-CN`/`zh-TW` 级区分。

**官方两处先例都把 `zh*` 映射成 `zh-CN`**：
- `dsh-client-locale/lib/client.js:1174`：`const language = snapshot.active === "zh" ? "zh-CN" : snapshot.active;`
- `/lib/main.js:7608-7616`：`locale.toLowerCase().startsWith("zh") ? {id:"zh-CN", messages:zh} : {id:"en", messages:en}`

→ 官方对 `zh` 的既定语义就是**简体中文**。

**映射规则表**（`osLanguages` = Client 侧 `globalThis.__DSH_LOCALE__?.read().languages`（Desktop，来自 `app.getPreferredSystemLanguages()`，`main.js:12077`）或 `navigator.languages`）：

| 输入 | 输出 `targetLanguage` | 判定依据 |
|---|---|---|
| `zh`（内置，最常见） | `osLanguages` 首项匹配 `zh-Hant`/`zh-TW`/`zh-HK`/`zh-MO` → **`zh-TW`**；否则 → **`zh-CN`** | 官方把 `zh` 定为 `zh-CN`；繁体细分只能靠系统语言二次判定 |
| `en`（内置） | **`en`** | `FALLBACK_LOCALE = "en"`（`client.js:1135`），正则接受裸 `en` |
| `ja`/`ko`/其他**外部语言包 id** | **原样透传** | `addLanguage` 要求 id 是 BCP-47 风格（`client.js:1297-1320`），本身合法 |
| OS `zh-Hans-CN` | **`zh-CN`** | script 优先：`Hans` → 简体，丢弃 region |
| OS `zh-Hant-TW` | **`zh-TW`** | `Hant` → 繁体 |
| OS `zh-Hans-HK` | **`zh-CN`** | **script 优先于 region**：`Hans` 一律简体 |
| OS `zh-Hant-HK` / `zh-Hant-MO` | **`zh-TW`** | `Hant` 一律繁体 |
| OS `zh_CN`（下划线，来自 `AppleLocale`） | **`zh-CN`** | 先做下划线→连字符归一化 |
| OS `ja-JP` / `ko-KR` / `fr-FR` | **`ja` / `ko` / `fr`** | 丢 region，保留主语言 |
| OS `en-US` / `en-GB` | **`en`** | 同上；`en` 已是插件预设 |
| 无法识别 / 空 | **`zh-CN`** | `DEFAULT_LANGUAGE`（`lib/state.js:25`），与 0.1.0 一致 |

**归一化算法**：

```
0. tag = tag.replace(/_/g, '-')          // AppleLocale 给 "zh_CN"，AppleLanguages 给 "zh-Hans-CN"
1. primary = tag.split('-')[0].toLowerCase()
2. 若 primary === 'zh'：
     script = 标签里的 4 字母段（Hans/Hant，大小写不敏感）
     'hant' → 'zh-TW'；'hans' → 'zh-CN'
     否则 region ∈ {TW, HK, MO} → 'zh-TW'；否则 → 'zh-CN'
3. 否则 → primary（丢弃所有子标签）
```

**下划线格式的实测来源**（两种格式归一到同一结果，保证「不管走哪条系统探测路，映射一致」）：

| 探测方式 | 原始值 | 归一化后 | 结果 |
|---|---|---|---|
| `defaults read -g AppleLocale` | `zh_CN` | `zh-CN` | `zh-CN` |
| `defaults read -g AppleLanguages` | `zh-Hans-CN` | 不变 | `zh-CN` |
| Swift `Locale.current.identifier` | `zh_CN` | `zh-CN` | `zh-CN` |
| Swift `Locale.preferredLanguages[0]` | `zh-Hans-CN` | 不变 | `zh-CN` |

**不做的事**：不把 `en-US` 原样透传。`targetLanguage` 的语义是「让模型用哪种语言思考」，地区变体无意义，只会让设置卡片出现 `en-US`/`en-GB` 噪声。

**完整兜底顺序**：

```
targetLanguage(auto) = map(uiLocale, osLanguages)
uiLocale    = ① locale.preference ② detectedLanguage（可选，默认关闭） ③ targetLanguage 配置值（默认 zh-CN）
osLanguages = ① __DSH_LOCALE__.read().languages（Desktop） ② navigator.languages（Web） ③ []
```

**可解释性**：auto 态下必须显示**来源**，不能只显示结果 ——
「跟随界面语言（`{preference}`）」/「跟随当前界面（`{detected}`）」/「未能识别，使用当前设定 `{fallback}`」。

### F. 与现有 6 字段的关系：定案方案甲

| 方案 | 结论 | 理由 |
|---|---|---|
| **甲** `languageMode: 'auto' \| 'manual'` | ✅ **定案** | 语义清晰；`targetLanguage` 的 BCP-47 契约完全不动；已装用户零迁移 |
| 乙 `targetLanguage` 允许 `'auto'` | ❌ 否 | **实测破坏现有校验**：`"auto"` → `REJECT: $.targetLanguage expect string to match regexp /^[A-Za-z]{2,3}(-[A-Za-z0-9]{2,8})*$/`；且 `client.js:32` 有同款正则，`/language` 命令、chips 高亮、`resolveLanguage` 全要改 |
| 丙 `autoDetect: boolean` | ❌ 否 | 「auto=true 时 targetLanguage 是什么」语义歧义；无法表达第三种模式；UI 要解释两控件联动 |

**新增字段**（既有 6 个的名字、类型、默认值、语义一律不动）：

```js
languageMode: z.union([z.const('auto'), z.const('manual')]).default('auto')
  .description('语言模式。auto=自动跟随界面语言（默认）；manual=固定使用 targetLanguage。').volatile(),
detectedLanguage: z.string().default('')
  .description('内部字段：Client 回写的已映射界面语言。仅 auto 且读不到 locale.preference 时使用。').volatile(),
```

**关键迁移规则**：`languageMode` 默认 `'auto'` 会**覆盖老用户手选的 `targetLanguage`**（如 `'ja'`）。实现必须在 `apply()` 里做一次性判定 —— 若 `targetLanguage` 存在且 ≠ `'zh-CN'` 而 `languageMode` 是默认值，按 `'manual'` 处理，并在设置卡片提示「检测到你设过固定语言，已切到手动」。

`resolveLanguage` 扩展（`/language` 命令覆盖仍最优先）：

```js
export function resolveLanguage(configured, { mode, autoValue } = {}) {
  if (languageOverride) return languageOverride;
  if (mode === 'manual') { const raw = typeof configured === 'string' ? configured.trim() : ''; return raw || DEFAULT_LANGUAGE; }
  return autoValue || DEFAULT_LANGUAGE;
}
```

**auto 态 UI 规格**（不能「点了没反应」）：

侧栏菜单 —— 第 1 项固定「自动（跟随界面）」，`aria-checked` 反映 `languageMode === 'auto'`；菜单头部「当前：」显示 **`自动（{解析结果 label}）`**，不能只写「自动」。选中具体语言时用**单次 `mutate` 批量**写 `languageMode='manual'` + `targetLanguage=code`（`ConfigForm.mutate` 支持 ops 数组，`dsh-client-ui-settings/lib/client.js:1165`），避免 revision 竞态留下半截状态。

设置卡片 —— 新增「语言模式」单选组；auto 态下 `targetLanguage` 输入框与 chips **禁用但显示解析结果**（不是清空），并显示「来源」一行（界面语言 / 当前界面 / 配置兜底）。

**不需要重启**：section 的 `text()` 是函数，`assemble()` 每 step 求值（`dsh-system-prompt/lib/index.js:388`）；`cachedUiLocale` 是闭包变量，`refreshUiLocale()` 一改，下一 step 的 system prompt 就是新语言。

### 实现要点（给实现工程师）

**Host 侧**：`readLocalePreference()` 用 `ctx.inject(['settings'])` 懒注入 + `describe()` 找 `ns==='locale'` + `settings/document-updated` 刷新缓存；**入口先判 `shouldAutoDetect()`（`languageMode !== 'manual'`），manual 态直接置 `null` 不读盘**；**`describe()` 绝不进 `text()`**（每 step 2–5 ms 不可接受）。三段 `text()` 改为读 `effectiveLanguage()`。

**Client 侧**：`ctx.inject(['locale'])` 拿服务（`dsh-client-locale/lib/client.js:1526 ctx.provide("locale", locale)`），`locale.subscribe(sync)` + 挂载时 `sync()`，值变才写 `detectedLanguage`（**可选增强，默认关闭**）。

**简化定案**：`detectedLanguage` 存的是 Client **已映射好的 `targetLanguage`**（如 `zh-TW`），不是原始 `active` —— 繁简判定需要 `osLanguages`，而只有 Client 有。Host 侧 `mapUiLocale` 只需处理 `preference` 这一条来源。

**约束遵守**：不监听 `system-prompt/assemble`（现有 C4 门禁继续为空）；不破坏既有 6 字段语义；auto 只选语言、不碰三档强度。

**四条必须避免的坑**：① `describe()` 进 `text()`；② 用 `Intl`/`LANG` 做系统语言兜底（中文用户会被判成 `en-US`）；③ 无条件回写 `detectedLanguage`（检测值变持久值、多端互相覆盖）；④ 忘掉 `languageMode` 默认 `auto` 会覆盖老用户手选的 `targetLanguage`。
